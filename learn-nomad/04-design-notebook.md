# 04 — Part D: First-principles design notebook

Sixteen topics in dependency order. Each: original problem → invariant → Nomad abstraction → exact paths → realistic failure → wrong mental model → test to read → Socratic question. Comparisons to Kubernetes, Temporal, and an agent-worker fleet appear where they sharpen the idea, with their limits stated.

---

## D1. Desired state, observed state, reconciliation

- **Problem:** operators express intent once; reality drifts (crashes, host loss, updates). Something must continuously compute "what should change."
- **Invariant:** intent and observation are stored in *separate fields* with *separate writers*; only a scheduler pass may turn a difference into actions.
- **Abstraction:** `Job` (intent), `Allocation.DesiredStatus`/`DesiredTransition` (intent per instance), `Allocation.ClientStatus`/`TaskStates` (observation), `Evaluation` (trigger), `AllocReconciler.Compute` (the diff), `Plan` (the actions).
- **Paths [source]:** `nomad/structs/alloc.go` (`DesiredStatus`, `ClientStatus`, `DesiredTransition`), `scheduler/reconciler/reconcile_cluster.go` (`ReconcileResults`, `computeGroup`, `computeStop`, `computeUpdates`, `placeAllocs`), `scheduler/reconciler/allocs.go` (`allocSet`, `AllocNameIndex`), `scheduler/reconciler/filters.go` (`classifyAllocs`, `filterByRescheduleable`), `client/client.go` `runAllocs` + `diffAllocs` (client-side reconcile).
- **Failure scenario:** a client reports `running` for an alloc whose desired status is `stop` (it has not yet pulled the update). No conflict: the scheduler ignores client status for stop decisions; the client will pull the `stop` and act. If instead the server *inferred* desired from observed, a partition would cause it to "adopt" stale processes.
- **Wrong model:** "There is a periodic controller loop." Nomad reconciles only when an evaluation exists; if no eval is created for a change, nothing reconciles (this is why `createNodeEvals` and `shouldCreateNodeEval` matter).
- **Test:** `scheduler/reconciler/reconcile_cluster_test.go` `TestReconciler_Place_Existing` and `TestReconciler_ScaleDown_Partial`.
- **Kubernetes comparison:** K8s controllers watch objects and reconcile continuously (level-triggered); Nomad is edge-triggered via evaluations, with `BlockedEvals` bridging "wait for capacity." Difference: in Nomad the reconciler and the placement logic live in the same scheduler pass, whereas K8s splits ReplicaSet controller (how many) from kube-scheduler (where).
- **Socratic:** If an eval were lost forever (never created), which desired/observed difference would silently persist, and which server mechanisms exist to create "catch-up" evals? (Look at `reapFailedEvaluations`, `periodicUnblockFailedEvals`, and what happens on node status changes.)

## D2. Job specs, task groups, tasks, allocation as the scheduling unit

- **Problem:** co-location and shared resources (network namespace, volumes) require grouping; independent scaling requires a count per group; failure isolation requires an identity per instance.
- **Invariant:** all tasks of one group instance run on one node with one shared allocation directory and network; the allocation is the unit of placement, accounting, and status.
- **Abstraction:** `Job` → `TaskGroup{Count, Tasks, Networks, Volumes, Services}` → `Task{Driver, Config, Resources}`; instance = `Allocation{Name: "job.group[i]", TaskGroup, NodeID, AllocatedResources}`.
- **Paths [source]:** `nomad/structs/structs.go` `Job`, `TaskGroup`, `Task`, `Job.Validate`, `TaskGroup.Validate`, `Task.Validate`, `Job.Canonicalize`; `nomad/job_endpoint_hooks.go` (`jobCanonicalizer`, `jobImpliedConstraints`); `scheduler/reconciler/allocs.go` `AllocNameIndex` (stable instance names `[0..count)`); `nomad/structs/alloc.go` `AllocatedResources`.
- **Failure scenario:** `count` decreases from 5 to 3. The reconciler must pick *which two* to stop deterministically (name index), not "any two," or a later scale-up would reuse names that still exist (`TestServiceSched_JobModify_ExistingDuplicateAllocIndex`).
- **Wrong model:** "Resources are on the task group." They are on each `Task.Resources`; the group's total is the sum, computed into `AllocatedResources` at placement.
- **Test:** `scheduler/generic_sched_test.go` `TestServiceSched_JobModify_CountZero`, `TestServiceSched_JobModify_InPlace`.
- **Agent-fleet analogy:** group = "one worker sandbox with its sidecars"; task = one process inside it. Limit: Nomad has no notion of a *conversation* or *tool call*; a task is a process, and its exit code is the only completion signal.
- **Socratic:** Why does an in-place update (`inplaceUpdate`) exist at all, and what field change forces a destructive update instead? (`scheduler/util.go` `tasksUpdated`.)

## D3. Nodes, fingerprints, resource models, eligibility

- **Problem:** the scheduler needs a truthful, comparable description of every machine, kept fresh, without every scheduler pass probing hardware.
- **Invariant:** a node's capacity and attributes in server state are produced only by the client's fingerprints (never edited by the scheduler), and placements only go to nodes that are `ready` and `eligible`.
- **Abstraction:** `Node{Attributes, NodeResources, ReservedResources, Status, SchedulingEligibility, ComputedClass, Drain}`; fingerprinters implementing `fingerprint.Fingerprint`; driver fingerprints feeding `Attributes["driver.<name>"]`.
- **Paths [source]:** `client/fingerprint/fingerprint.go` (`Fingerprint` interface, `Periodic`), `client/fingerprint/{cpu,memory,storage,network,host,arch,...}.go`, `client/client.go` `setupNode`, `updateNodeFromFingerprint`, `watchNodeUpdates`; `nomad/node_endpoint.go` `Register`, `UpdateEligibility`, `UpdateDrain`; `nomad/structs/structs.go` `Node.Ready`, `Node.ComputeClass` (`node_class.go`), `NodeStatus*`, `NodeSchedulingEligible`; FSM `applyUpsertNode` → `blockedEvals.Unblock(node.ComputedClass, ...)`.
- **Failure scenario:** a node's fingerprint changes (driver becomes unhealthy). `Register`/`UpdateStatus` with `shouldCreateNodeEval` creates evals; the scheduler's `DriverChecker` now filters the node out for jobs using that driver; existing allocs are not moved unless the node is drained or down — a common surprise.
- **Wrong model:** "Ineligible means down." Ineligible nodes keep running what they have and still heartbeat; they just receive no new placements (`evaluateNodePlan` still allows in-place updates via `AllocSubset`).
- **Test:** `nomad/node_endpoint_test.go` `TestClientEndpoint_Register`, `TestClientEndpoint_UpdateStatus_GetEvals`; `client/client_test.go` `TestClient_Fingerprint_Periodic`; `nomad/fsm_test.go` `TestFSM_UpdateNodeEligibility_Unblock`.
- **Socratic:** `ComputedClass` groups nodes with identical scheduling-relevant attributes so `EvalContext` can cache feasibility per class. What attribute change would silently make two nodes *not* share a class, and why does that matter for blocked-eval unblocking?

## D4. Server state, Raft, leader duties, state-store/FSM boundary

- **Problem:** multiple servers must agree on one history of writes and survive server loss; some coordination (queues, timers) must exist exactly once.
- **Invariant:** every durable write is a Raft log entry applied deterministically by every server's FSM; leader-only structures are derived from durable state and rebuilt on election.
- **Abstraction:** `Server` + `nomadFSM` + `StateStore` (memdb, snapshot isolation); `raftApply`; leader loop with `establishLeadership`/`revokeLeadership`.
- **Paths [source]:** `nomad/server.go` (`NewServer`, `setupRaft`, `setupRPC`, `setupWorkers`), `nomad/rpc.go` (`raftApply`, `raftApplyFuture`, `forward`, `blockingRPC`), `nomad/fsm.go` (`Apply`, `Snapshot`, `Restore`), `nomad/state/state_store.go` (`Snapshot`, `SnapshotMinIndex`, `WriteTxnMsgT`), `nomad/leader.go` (`monitorLeadership`, `leaderLoop`, `establishLeadership`, `restoreEvals`, `revokeLeadership`), `nomad/structs/structs.go` `MessageType` constants; [repo-doc] `contributing/architecture-state-store.md` (determinism, copy-before-mutate, write skew).
- **Failure scenario:** leader loses leadership while `planApply` has issued `raftApplyFuture` for a plan. The future errors; the worker nacks; the new leader's `restoreEvals` re-enqueues the eval; a fresh scheduling pass runs. If the entry *had* committed before the error surfaced, the new pass sees the allocs and reconciles to a no-op. Heartbeat timers are re-armed with `FailoverHeartbeatTTL` so nodes are not mass-marked down.
- **Wrong model:** "The state store is a database you can write to from a handler." Handlers write only through `raftApply`; direct `StateStore` writes exist only inside the FSM (and tests).
- **Test:** `nomad/leader_test.go` `TestLeader_EvalBroker_Reset`, `TestLeader_PlanQueue_Reset`, `TestLeader_RevokeLeadership_MultipleTimes`; `nomad/fsm_test.go` `TestFSM_RegisterJob`; `nomad/state/state_store_test.go` `TestStateStore_Blocking_MinQuery`.
- **Temporal comparison:** Temporal persists workflow *history* events in a database with sharded ownership; Nomad persists *state* via a replicated log with a single leader. Both give "durable decision records," but Temporal's unit is a workflow execution with replayable history, while Nomad's is an allocation with a status; Nomad has no replay.
- **Socratic:** Why must the FSM never call `time.Now()` or `uuid.Generate()`, and where in `Job.Register` are those values created instead?

## D5. Evaluation lifecycle; why not schedule inside the submit request

- **Problem:** scheduling can be slow (many nodes), may need retries against concurrent writes, and must also happen for events that are *not* user requests (node down, task failure, deployment step, delayed reschedule). Doing it inside `Job.Register` would couple API latency to cluster size and lose the ability to re-run.
- **Invariant:** every reason to reconsider a job becomes a durable eval with a `TriggeredBy`; evals for one job are processed one at a time; an eval that cannot be completed is either blocked (waiting for capacity) or failed-with-follow-up, never silently dropped.
- **Abstraction:** `Evaluation`, `EvalBroker` (ready/unack/blocked/delayed/failed queues), `BlockedEvals`, worker `run` loop, `Planner.CreateEval/UpdateEval/ReblockEval`.
- **Paths [source]:** `nomad/structs/eval.go` (triggers, statuses, `MakePlan`, `CreateBlockedEval`, `CreateFailedFollowUpEval`, `NextRollingEval`), `nomad/eval_broker.go`, `nomad/blocked_evals.go`, `nomad/eval_endpoint.go`, `nomad/worker.go`, `nomad/leader.go` (`reapFailedEvaluations`, `reapDupBlockedEvaluations`, `reapCancelableEvaluations`, `periodicUnblockFailedEvals`), `nomad/core_sched.go` (`evalGC`); [repo-doc] `contributing/architecture-eval-states.md`, `architecture-eval-triggers.md`.
- **Failure scenario:** a scheduler panics on a malformed eval. `Process` recovers the panic, returns an error, the worker nacks; after `EvalDeliveryLimit` (3) the broker parks it in the failed queue; `reapFailedEvaluations` marks it `failed` and creates a `failed-follow-up` eval with a delay, bounding the retry storm.
- **Wrong model:** "Blocked evals are retried on a timer." They are unblocked by *state changes* (`BlockedEvals.Unblock` from FSM on node upserts/status/eligibility, `UnblockNonNodeResources`, quota) plus `UnblockFailed` periodically for those that failed for non-capacity reasons.
- **Test:** `nomad/eval_broker_test.go` `TestEvalBroker_Serialize_DuplicateJobID`, `TestEvalBroker_Nack_Timeout`; `nomad/blocked_evals_test.go` `TestBlockedEvals_UnblockEligible`; `scheduler/generic_sched_test.go` `TestServiceSched_EvaluateBlockedEval`.
- **Temporal comparison:** Temporal's task queues deliver workflow/activity tasks to workers with lease + heartbeat + retry, similar to `Dequeue` token + nack timeout + delivery limit. Difference: a Temporal task is one step of a user workflow; a Nomad eval is a whole-job reconciliation whose output is a placement plan, and per-job serialization is built into the broker.
- **Socratic:** The broker serializes evals per job. What would break if two evals for the same job ran concurrently on two workers, given that the plan applier already checks node capacity?

## D6. Scheduler filtering, scoring, bin packing, constraints, affinities

- **Problem:** choose a node quickly among thousands, respecting hard requirements and soft preferences, while keeping utilization sane.
- **Invariant:** constraints are never violated; scoring only orders *feasible* nodes; feasibility for a computed class is cached per eval so repeated work is avoided.
- **Abstraction:** iterator pipeline: `FeasibleIterator` chain → `RankIterator` chain → `LimitIterator` → `MaxScoreIterator`, driven by `GenericStack.Select` with `EvalContext` metrics.
- **Paths [source]:** `scheduler/feasible/stack.go` (`NewGenericStack`, `Select`, `SetJob`, `SetNodes`), `scheduler/feasible/feasible.go` (`ConstraintChecker`, `DriverChecker`, `HostVolumeChecker`, `CSIVolumeChecker`, `NetworkChecker`, `DeviceChecker`, `DistinctHostsIterator`, `DistinctPropertyIterator`, `FeasibilityWrapper`), `scheduler/feasible/rank.go` (`BinPackIterator`, `JobAntiAffinityIterator`, `NodeReschedulingPenaltyIterator`, `NodeAffinityIterator`, `ScoreNormalizationIterator`, `PreemptionScoringIterator`), `scheduler/feasible/spread.go`, `scheduler/feasible/select.go`, `scheduler/feasible/context.go` (`EvalContext`, `EvalCache`, `ComputedClassFeasibility`), `nomad/structs/funcs.go` (`AllocsFit`, `ScoreFitBinPack`, `ScoreFitSpread`), `nomad/structs/structs.go` (`Constraint`, `Affinity`, `Spread`).
- **Failure scenario:** every node is feasible but the best-scoring one is full by the time the plan is applied (another job landed). The plan is rejected on that node; the worker refreshes state and reruns; `NodeReschedulingPenaltyIterator` and the `LimitIterator` skip logic make the retry pick differently.
- **Wrong model:** "Affinity weight 100 forces placement." It only adds to the normalized score; a constraint is the only way to force.
- **Test:** `scheduler/feasible/stack_test.go` `TestServiceStack_Select_ConstraintFilter`, `TestServiceStack_Select_BinPack_Overflow`; `scheduler/feasible/rank_test.go` `TestBinPackIterator_NoExistingAlloc`, `TestBinPackIterator_PlannedAlloc`; `scheduler/feasible/feasible_test.go` `TestNetworkChecker`.
- **Kubernetes comparison:** kube-scheduler has Filter and Score plugin phases, the same two-phase shape. Difference: Nomad's `LimitIterator` intentionally scores only a handful of feasible nodes for service jobs (speed over optimality), and Nomad supports preemption and spread inside the same pipeline rather than as separate controllers.
- **Socratic:** `BinPackIterator` evaluates fit using `AllocsFit` with *proposed* allocations from the current plan (`ctx.Plan()`), not just existing ones. Why is that necessary within a single evaluation that places three allocations?

## D7. Plans, plan application, optimistic concurrency, safe resource accounting

- **Problem:** many schedulers run in parallel on stale snapshots; two may pick the same node; the leader must accept only what still fits, without stopping the world.
- **Invariant:** a plan is applied only against state that includes the plan's `SnapshotIndex` and all prior applied plans; per-node fit is re-checked; partial acceptance is explicit; the worker learns the refresh index.
- **Abstraction:** `Plan{SnapshotIndex, EvalToken, NodeAllocation, NodeUpdate, NodePreemptions, Deployment}`, `PlanQueue`, `planner.planApply`, `PlanResult{RefreshIndex, RejectedNodes}`, `ApplyPlanResultsRequest`.
- **Paths [source]:** `nomad/plan_endpoint.go` `Submit`, `nomad/plan_queue.go`, `nomad/plan_apply.go` (`planApply`, `snapshotMinIndex`, `evaluatePlan`, `evaluatePlanPlacements`, `evaluateNodePlan`, `applyPlan`, `asyncPlanWait`, `isValidForDownNode`, `isValidForDisconnectedNode`), `nomad/state/state_store.go` `UpsertPlanResults`, `nomad/structs/plan.go` (`FullCommit`, `NormalizeAllocations`), `nomad/worker.go` `SubmitPlan`.
- **Failure scenario:** node N is marked ineligible after repeated plan rejections (`IneligibleNodes` in `UpsertPlanResults` with a warning linking to the "port-plan-failure" doc). This protects the cluster from a node whose fingerprint disagrees with the scheduler's view, at the cost of an operator needing to re-enable it.
- **Wrong model:** "The plan applier re-runs the scheduler." It only *validates fit and node status*; it never chooses different nodes. Choice is always the worker's.
- **Test:** `nomad/plan_apply_test.go` `TestPlanApply_EvalPlan_Partial`, `TestPlanApply_EvalNodePlan_NodeFull`; `nomad/plan_endpoint_test.go` `TestPlanEndpoint_ApplyConcurrent`; `nomad/worker_test.go` `TestWorker_SubmitPlan_MissingNodeRefresh`.
- **Agent-fleet analogy:** this is exactly the "two coordinators both promise the last GPU" problem; the answer is one serialization point that validates promises against durable reservations. Limit: Nomad reserves by declared resources; it cannot protect against a worker that lies about or exceeds its usage.
- **Socratic:** `planApply` keeps a snapshot with *optimistic* updates while plans are in flight and only refreshes when `inFlightPlans == 0`. What anomaly would appear if it refreshed the snapshot while a plan was still uncommitted?

## D8. Client/server protocol, heartbeats, allocation delivery

- **Problem:** thousands of clients must learn about their work and prove liveness without overwhelming the leader, and must keep running during server outages.
- **Invariant:** clients pull (blocking queries, stale-allowed on followers); heartbeats go to the leader and are rate-shaped; a node's status is changed only by the leader on TTL expiry or by the client's own report.
- **Abstraction:** `Node.Register`, `Node.UpdateStatus` (heartbeat), `Node.GetClientAllocs` + `Alloc.GetAllocs` (delivery), `Node.UpdateAlloc` (status), `nodeHeartbeater` timers, client `servers` list with rediscovery.
- **Paths [source]:** `client/client.go` (`registerAndHeartbeat`, `retryRegisterNode`, `registerNode` [uses `UnauthenticatedRPC` for `Node.Register`], `updateNodeStatus` [updates `heartbeatTTL` and server list from the reply], `watchAllocations`, `allocSync`), `client/rpc.go` (`RPC`, `rpc`, `rpcRetryWatcher`), `nomad/node_endpoint.go` (`Register`, `UpdateStatus`, `GetClientAllocs`, `UpdateAlloc`, `constructNodeServerInfoResponse`), `nomad/heartbeat.go`, `nomad/config.go` (`MinHeartbeatTTL`, `MaxHeartbeatsPerSecond`, `HeartbeatGrace`, `FailoverHeartbeatTTL`), `nomad/auth/auth.go` (`AuthenticateClientOnly`, node identity).
- **Failure scenario:** all servers restart. Clients keep tasks running, fail heartbeats, `triggerDiscovery`, and re-register when servers return; the new leader arms failover TTLs; nodes that re-register from `down` get a `NodeHeartbeatEventReregistered` event and go through `initializing` until they re-report allocs (`LastAllocUpdateIndex > LastMissedHeartbeatIndex`).
- **Wrong model:** "Heartbeat carries allocation status." It carries only node status; alloc status is a separate, batched RPC (`allocSync`).
- **Test:** `client/client_test.go` `TestClient_Heartbeat`, `TestClient_WatchAllocs`; `nomad/node_endpoint_test.go` `TestClientEndpoint_UpdateStatus_HeartbeatOnly`, `TestClientEndpoint_GetClientAllocs_Blocking`; `nomad/heartbeat_test.go` `TestHeartbeat_ResetHeartbeatTimer_Nonleader`.
- **Socratic:** Why does `watchAllocations` fetch alloc *IDs and indexes* first and only then fetch full allocations, and what race does the "missing expected alloc → sleep and retry" branch handle?

## D9. Allocation runner, task runner, lifecycle hooks, task-driver boundary

- **Problem:** turning an allocation into processes needs ordered setup (dirs, network, secrets, artifacts, templates, service registration) and ordered teardown, with restart semantics per task and per group, across many driver types.
- **Invariant:** hooks run in a fixed order with persisted progress; the driver is only asked to start after prestart succeeds; task state transitions are persisted before being reported; the driver handle is persisted so the client can recover.
- **Abstraction:** `allocRunner` (alloc-level hooks in `alloc_runner_hooks.go`), `TaskRunner` (task-level hooks in `task_runner_hooks.go`), `RestartTracker`, `DriverPlugin`/`TaskHandle`/`ExitResult`, `driverManager.Dispense`.
- **Paths [source]:** `client/allocrunner/alloc_runner.go`, `alloc_runner_hooks.go`, `client/allocrunner/interfaces/`, `client/allocrunner/tasklifecycle/` (leader/main/prestart/poststop coordination), `client/allocrunner/taskrunner/task_runner.go`, `task_runner_hooks.go`, `lifecycle.go` (`Kill`), `restarts/restarts.go`, `driver_handle.go`, `lazy_handle.go`; `plugins/drivers/driver.go`, `plugins/drivers/task_handle.go`; `drivers/rawexec/driver.go`, `drivers/mock/driver.go`; `client/pluginmanager/drivermanager/manager.go`.
- **Failure scenario:** the external driver plugin process crashes while tasks run. `TestTaskRunner_RecoverFromDriverExiting` covers it: the task runner detects the lost handle and, via the driver manager's reattach/restart, recovers or restarts the task per policy.
- **Wrong model:** "Killing an alloc kills processes immediately." `preKillHooks` and `ShutdownDelay` run first; `KillTimeout` bounds the graceful window; only then `StopTask`/`DestroyTask`.
- **Test:** `client/allocrunner/alloc_runner_test.go` `TestAllocRunner_TaskLeader_KillTG`, `TestAllocRunner_Lifecycle_Poststart`; `client/allocrunner/taskrunner/task_runner_linux_test.go` `TestTaskRunner_Stop_ExitCode`, `TestTaskRunner_RestartTask`; `restarts_test.go` `TestClient_RestartTracker_ModeDelay`.
- **Agent-fleet analogy:** hooks are the "prepare sandbox, fetch tool bundle, inject credentials, register with the router" steps; the driver is the sandbox runtime. Limit: Nomad hooks have no knowledge of the application protocol; a tool call failing inside a running process is invisible unless it changes the exit code or a health check.
- **Socratic:** `addAlloc` writes the allocation to BoltDB *before* creating the runner, and `runDriver` persists the handle *before* reporting `running`. Enumerate the crash points between "driver started" and "state reported" and say what `Restore` does at each.

## D10. Client local state and recovery after client-agent restart

- **Problem:** the client process restarts (upgrade, crash) while tasks are running; it must re-adopt them, not double-start or orphan them.
- **Invariant:** BoltDB is the source of truth for "what I was running"; each task's driver handle is persisted; restore attempts `RecoverTask` and falls back to failing the task (restart policy applies); server allocs win over local allocs once reconnected.
- **Abstraction:** `StateDB` interface with `BoltStateDB`; `restoreState` → `NewAllocRunner` → `Restore` → `TaskRunner.Restore` → `restoreHandle`; acknowledged-state tracking (`PutAcknowledgedState`) for status resync.
- **Paths [source]:** `client/state/interface.go`, `db_bolt.go`, `upgrade.go`, `12types.go`; `client/client.go` `restoreState`, `handleInvalidAllocs`, `saveState`, `periodicSnapshot`; `client/allocrunner/alloc_runner.go` `Restore`; `client/allocrunner/taskrunner/task_runner.go` `Restore`, `restoreHandle`, `persistLocalState`; `plugins/drivers/driver.go` `RecoverTask`.
- **Failure scenario:** the alloc dir is missing on restore (`TestAllocRunner_Restore_MissingAllocDir`) or a prerun hook fails during restore (`TestClient_AllocPrerunErrorDuringRestore`); the alloc is marked failed rather than crashing the agent.
- **Wrong model:** "Local state is a cache of server state." It also holds driver-specific reattach data that the server never sees.
- **Test:** `client/client_test.go` `TestClient_SaveRestoreState`; `client/state/db_test.go` `TestStateDB_TaskState`, `TestStateDB_Upgrade`; `task_runner_linux_test.go` `TestTaskRunner_Restore_Running`, `TestTaskRunner_Restore_Dead`.
- **Socratic:** When a client restores an allocation that the server has since marked `stop`, which loop notices, and in what order do "restore local" and "pull from server" happen in `client.init`/`Run`?

## D11. Health checks, service registration, the Consul boundary

- **Problem:** "running" is not "serving"; deployments need a real signal, and other services need to find instances.
- **Invariant:** service registration follows task lifecycle hooks (register at poststart, update on alloc update, deregister on kill/exit); health for deployments is judged on the client and reported once; Consul is an external system with its own agent state that must be *synced*, not assumed.
- **Abstraction:** `serviceregistration.Handler` with two providers (Consul `ServiceClient`, Nomad-native `nsd`), `checks.Client` for Nomad checks, `allochealth.Tracker`, `allocHealthWatcherHook`.
- **Paths [source]:** `client/serviceregistration/service_registration.go`, `client/serviceregistration/wrapper/`, `client/serviceregistration/nsd/nsd.go`, `client/serviceregistration/checks/client.go`, `command/agent/consul/service_client.go` (`Run`, `sync`, `commit`, `RegisterWorkload`), `client/allocrunner/taskrunner/service_hook.go`, `client/allocrunner/group_service_hook.go`, `client/allocrunner/checks_hook.go`, `client/allocrunner/health_hook.go`, `client/allochealth/tracker.go`, `nomad/state/state_store_service_registration.go` (native service catalog on servers).
- **Failure scenario:** Consul agent restarts and forgets registrations; `ServiceClient.sync` periodically reconciles Nomad's expected set against `agent/services` and re-registers. Meanwhile a deployment's `HealthyDeadline` may expire because checks vanished, failing the deployment spuriously.
- **Wrong model:** "Nomad checks health of every allocation continuously and restarts unhealthy ones." Only during deployments (health hook) or when a check has `check_restart` configured does health drive actions; otherwise checks are informational.
- **Test:** `client/allochealth/tracker_test.go` `TestTracker_ConsulChecks_HealthyToUnhealthy`, `TestTracker_NomadChecks_Unhealthy`; `client/allocrunner/taskrunner/service_hook_test.go`; `command/agent/consul/service_client_test.go`.
- **Socratic:** The health tracker reports at most one verdict per deployment per alloc (`HasHealth`). Why is a single write, rather than a continuously updated boolean, the right design given `contributing/architecture-state-store.md`'s write-skew warning?

## D12. Task failure, restart policy, reschedule policy, deployments, canaries, rollbacks

- **Problem:** distinguish transient crashes (restart in place) from persistent failures (move elsewhere) from bad releases (stop rolling and revert), each with bounded retries.
- **Invariant:** restart decisions are client-local and bounded by `RestartPolicy{Attempts, Interval, Delay, Mode}`; reschedule decisions are scheduler-side, bounded by `ReschedulePolicy{Attempts, Interval, Delay, DelayFunction, MaxDelay, Unlimited}` and recorded in `RescheduleTracker`; deployment progress is gated by health counts and deadlines with explicit `failed`/`successful` terminal states; auto-revert uses the latest *stable* job version.
- **Abstraction:** `RestartTracker`; `Allocation.ShouldReschedule/RescheduleEligible/NextRescheduleTime`; reconciler `filterByRescheduleable`, `updateByReschedulable`, `createRescheduleLaterEvals`; `Deployment{TaskGroups: DeploymentState{DesiredTotal, PlacedAllocs, HealthyAllocs, UnhealthyAllocs, DesiredCanaries, PlacedCanaries, Promoted, ProgressDeadline}}`; `deploymentWatcher.watch/shouldFail/latestStableJob`; `UpdateStrategy{MaxParallel, Canary, AutoPromote, AutoRevert, MinHealthyTime, HealthyDeadline, ProgressDeadline}`.
- **Paths [source]:** `client/allocrunner/taskrunner/restarts/restarts.go`; `nomad/structs/alloc.go` (reschedule methods, `RescheduleTracker` in `structs.go`); `scheduler/generic_sched.go` `UpdateRescheduleTracker`, `markFailedToReschedule`; `scheduler/reconciler/reconcile_cluster.go` (`computeCanaries`, `cancelUnneededCanaries`, `computeDestructiveUpdates`, `createDeployment`, `isDeploymentComplete`, `setDeploymentStatusAndUpdates`); `nomad/deploymentwatcher/deployment_watcher.go` (`PromoteDeployment`, `FailDeployment`, `handleRollbackValidity`, `getDeploymentProgressCutoff`); `nomad/deployment_endpoint.go`; `nomad/structs/deployment.go`.
- **Failure scenario:** a new job version crashes on start. Restart policy retries on the client; when exhausted the alloc is `failed`; the deployment watcher sees `UnhealthyAllocs` exceed tolerance or `ProgressDeadline` passes → `FailDeployment`; with `AutoRevert`, `latestStableJob` is re-registered as a new version; a new deployment rolls it. `TestWatcher_SetAllocHealth_Unhealthy_Rollback` and `TestReconciler_FailedDeployment_AutoRevert_CancelCanaries` cover it.
- **Wrong model:** "Reschedule delay is applied by the client." It is a *server-side delayed eval* (`WaitUntil` in the broker's delay heap).
- **Test:** `restarts_test.go` `TestClient_RestartTracker_ModeFail`; `scheduler/generic_sched_test.go` `TestServiceSched_Reschedule_Later`, `TestDeployment_FailedAllocs_Reschedule`; `reconcile_cluster_test.go` `TestReconciler_NewCanaries`, `TestReconciler_PromoteCanaries_Unblock`; `deployments_watcher_test.go` `TestWatcher_AutoPromoteDeployment`, `TestWatcher_PauseDeployment_IgnoreProgressDeadline`.
- **Kubernetes comparison:** K8s Deployment controller manages ReplicaSets with `maxSurge`/`maxUnavailable` and rollback to a revision; Nomad's deployment is per job version with canaries and promotion as first-class states. Difference: K8s readiness probes gate rollout continuously; Nomad's health verdict is a one-time client decision within a deadline.
- **Socratic:** With `Attempts = 3, Interval = 1h, Unlimited = false`, what happens to the fourth failure in an hour, and what *new* event is required before the job gets another allocation?

## D13. Node failure, partitions, server failure, leadership changes

- **Problem:** "unreachable" is indistinguishable from "dead"; acting too early duplicates work, too late loses availability; the leader itself can fail mid-decision.
- **Invariant:** node status changes only on the leader; disconnected-vs-down is decided from per-alloc policy; replacements are bounded and tracked; on reconnect exactly one copy survives per the group's reconcile strategy; leader change never loses a committed write and never double-applies an uncommitted one.
- **Abstraction:** `NodeStatusDisconnected`, `DisconnectStrategy{LostAfter, Replace, Reconcile, StopOnClientAfter}`, `Allocation.ClientStatus = unknown`, `EvalTriggerMaxDisconnectTimeout`, `EvalTriggerReconnect`, `reconcileReconnecting`, `reconnecting_picker.go`; failover TTLs.
- **Paths [source]:** `nomad/heartbeat.go` (`invalidateHeartbeat`, `disconnectState`), `nomad/node_endpoint.go` (`UpdateStatus` transition table, `nodeStatusTransitionRequiresEval`, `UpdateAlloc` reconnect eval), `nomad/structs/group.go` (`DisconnectStrategy`, `ReconcileOption*`), `nomad/structs/alloc.go` (`DisconnectTimeout`, `Expired`, `NeedsToReconnect`, `LastUnknown`), `scheduler/util.go` `taintedNodes`, `scheduler/reconciler/filters.go` (`classifyAllocs`, `delayByLostAfter`, `delayByStopAfter`), `scheduler/reconciler/reconcile_cluster.go` (`computeDisconnecting`, `computeReconnecting`, `reconcileReconnecting`, `createTimeoutLaterEvals`), `scheduler/reconciler/reconnecting_picker.go`, `nomad/plan_apply.go` (`isValidForDisconnectedNode`, `isValidForDownNode`), `nomad/leader.go` (`revokeLeadership`, `establishLeadership`), `nomad/config.go` `FailoverHeartbeatTTL`.
- **Failure scenario:** network partition isolates client A for 5 minutes with `lost_after = 10m, replace = true`. Leader marks A `disconnected`, allocs `unknown`, places replacements on B. A reconnects at minute 5: reconnect eval; `Reconcile = best_score` picks one copy per instance and stops the other. If A returned at minute 11, the `max-disconnect-timeout` eval would already have marked the originals `lost`, and A would be told to stop them.
- **Wrong model:** "Raft protects against split brain for clients too." Raft protects *server* state; a client on the minority side of a partition keeps running whatever it has. Duplicate execution is possible by design when `replace = true`.
- **Test:** `nomad/heartbeat_test.go` `TestHeartbeat_InvalidateHeartbeat_DisconnectedClient`, `TestHeartbeat_Server_HeartbeatTTL_Failover`; `scheduler/generic_sched_test.go` `TestServiceSched_Client_Disconnect_Creates_Updates_and_Evals`; `reconcile_cluster_test.go` `TestReconciler_Disconnected_Client`, `TestReconciler_Disconnect_UpdateJobAfterReconnect`; `client/client_test.go` `TestClient_ReconnectAllocs`; `nomad/leader_test.go` `TestLeader_LeftLeader`.
- **Agent-fleet analogy:** this *is* the "worker goes silent mid-tool-call" problem. Nomad gives you: bounded wait, optional replacement, and a reconcile rule on return. Limit: it cannot make the tool call idempotent; that is the application's job (idempotency keys, external dedupe).
- **Socratic:** Why does `Node.UpdateStatus` force a `disconnected → initializing` step (instead of straight to `ready`) until the client has re-reported its allocations?

## D14. ACLs, workload identity, security boundaries

- **Problem:** humans, clients, servers, and running workloads all call RPCs; each must be authenticated differently and authorized narrowly; workloads need credentials without operators minting tokens.
- **Invariant:** every RPC handler authenticates before forwarding and authorizes with an `acl.ACL` after; client-only RPCs cannot be called with a human token; workload identities are JWTs signed by the server keyring and bound to an allocation.
- **Abstraction:** `acl.Policy`/`acl.ACL`, `auth.Authenticator` (`Authenticate`, `ResolveACL`, `AuthenticateClientOnly`, `AuthenticateServerOnly`, `VerifyClaim`), `WorkloadIdentity`/`IdentityClaims`/`SignedWorkloadIdentity`, `Encrypter` (keyring), client `widmgr`, task `identity_hook`.
- **Paths [source]:** `acl/acl.go`, `acl/policy.go`, `nomad/acl.go`, `nomad/auth/auth.go`, `nomad/encrypter.go` (`SignClaims`, `VerifyClaim`), `nomad/plan_apply.go` `signAllocIdentities`, `nomad/structs/workload_id.go`, `client/widmgr/`, `client/allocrunner/identity_hook.go`, `client/allocrunner/taskrunner/identity_hook.go`; [repo-doc] `contributing/checklist-rpc-endpoint.md` authentication rules.
- **Failure scenario:** keyring not yet initialized on a new leader → `applyPlan` cannot sign identities → plan fails (`TestPlanApply_KeyringNotReady`); scheduling stalls until `initializeKeyring` completes.
- **Wrong model:** "A nil ACL means allow." The checklist explicitly forbids nil checks; `acl` methods reject nil.
- **Test:** `nomad/auth/auth_test.go` `TestAuthenticateClientOnly`, `TestResolveClaims`; `acl/acl_test.go` `TestAllowNamespace`; `nomad/job_endpoint_test.go` `TestJobEndpoint_Register_ACL`.

## D16. Plugin architecture and external task drivers (overview only)

- **Problem:** runtimes differ (containers, VMs, raw binaries) and evolve independently of Nomad.
