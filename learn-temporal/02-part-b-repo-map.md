## Why the "Read now" items are conceptually central, not merely frequent

- **Frontend handler + interceptor chain**: it is the *only* place where a request can be rejected without any durable side effect. Everything after it is inside the consistency boundary. Understanding "validation happens here, state happens there" is the first ownership boundary.
- **History `api/startworkflow`, `api/update_workflow_util.go`, `workflow/context.go`, `shard/context_impl.go`**: these four files are the "state transition" pattern the architecture doc describes: lock execution → mutate in-memory mutable state → close transaction → conditional persistence write fenced by RangeID → notify queues. Every other RPC is a variation.
- **`MutableState` + `HistoryBuilder` + `TaskGenerator`**: the projection, the log, and the outbox, in one object. If you understand how an `AddXEvent` call both appends an event and generates a task, you understand event sourcing as Temporal does it.
- **Shard hashing + RangeID fencing**: the reason two History hosts cannot both write the same execution, even when membership is stale.
- **`queues/executable.go` + transfer executor**: the consumer side of the outbox, where at-least-once delivery meets "is this task still relevant?" checks (`Stamp`, `ScheduledEventID`, `Attempt`, version).
- **Matching engine + partition manager + matcher**: the pull model and sync-match, plus the callback to History (`RecordWorkflowTaskStarted`) that turns "offered" into "started" durably before the Worker sees the task.
- **Persistence interfaces + error types**: the contract that all the above relies on. You do not need the implementations yet, only the promise.
- **Functional test base**: the fastest way to *observe* every claim above as a real history.
